## 1. MDOF 물리모델 (Multi-Degree-of-Freedom)

### 1-1. 무엇인가
유압 실린더 힘·모터 토크 등 입력값으로 유량의 속도·가속도를 물리 수식으로 예측하는 다자유도 운동방정식 기반 정상 기준 모델. "정상 상태에서 센서가 어떻게 움직여야 하는가"를 데이터가 아니라 물리 법칙으로 먼저 정의하는 접근.

### 1-2. 왜 강점이 되나 (면접 어필 포인트)
순수 데이터 기반 AE는 "왜 그게 정상인지" 물리적 근거가 없다. 물리모델을 정상 기준으로 깔면 **도메인 지식 + AI 결합**이라는 산업 AI의 핵심 차별점이 생긴다. "라벨 없는 환경에서 물리 법칙으로 정상을 정의하고, AI로 잔차를 학습한다"는 서사는 제조AI 직무(원프레딕트·고영 등)에서 강하게 먹힌다.

### 1-3. 구현해야 할 것
1. **운동방정식 정의**: 펌프-유압 시스템의 MDOF 모델 수립. 입력(모터 토크 T, 유압 실린더 힘 F) → 출력(유량 Q, 유량 가속도 dQ/dt) 전달함수. 펌프 기계공학 문헌·교과서 근거 명시 (현재 출처 표기 0 → 반드시 레퍼런스 박을 것).
2. **파라미터 동정(system identification)**: 합성 데이터(또는 향후 실측)에서 관성·감쇠·강성 계수 추정.
3. **검증**: MDOF 예측 유량 vs 실제(합성) 유량 잔차 분포 시각화. 정상 구간에서 잔차가 0 근방인지 확인.

### 1-4. 완료 시 포트폴리오 격상
- 발화: "물리 모델로 정상 유량을 먼저 정의하고, 그 위에서 이상을 잡았습니다" (현재는 쓸 수 없음 → 구현 후 가능)
- CEDR 카탈로그에 신규 행 P-006으로 등재 (C1: MDOF 모듈 파일·라인, C2: 잔차 정의, C3: 검증 데이터, C4: 가정)

## 2. NN 보정 학습 (Residual Correction)

### 2-1. 무엇인가
MDOF 물리모델이 설명하지 못하는 부분(마찰·열변형·비선형 변동)을 신경망이 잔차(Residual = 실제 − MDOF예측)로 학습. 물리모델이 뼈대, NN이 현장 특성을 흡수하는 하이브리드 구조.

### 2-2. 의존성
**§1 MDOF가 선행 조건.** MDOF 예측이 있어야 잔차를 정의할 수 있다. MDOF 없이 NN 보정 단독은 성립 불가.

### 2-3. 구현해야 할 것
1. **잔차 타깃 구성**: `residual = sensor_actual − mdof_predict`. 정상 구간에서 이 잔차를 최소화하도록 NN 학습.
2. **현재 AE와의 관계 정리**: 지금의 순수 AE를 (a) MDOF 잔차를 입력으로 받는 구조로 재설계할지, (b) MDOF 보정 후 AE에 넣을지 아키텍처 결정.
3. **손실함수·학습곡선 기록**: train/val loss curve 저장 (`MODEL_CHANGELOG.md`에 Phase로 기록).
4. **성능 비교**: 순수 AE(현재) vs MDOF+NN 보정 AE의 F1·FAR 비교 그래프. **이 비교표가 면접에서 "왜 둘을 결합했나" 질문의 핵심 답변**이 된다.

### 2-4. 완료 시 포트폴리오 격상
- 발화: "물리모델 위에 NN 보정을 얹어 현장 노이즈를 흡수했고, 순수 AE 대비 FAR을 X% 낮췄습니다" (비교 수치 확보 후)

## 3. Cpk 1.67 (공정능력지수)

### 3-1. 무엇인가
공정능력지수 Cpk = min[(USL−μ)/3σ, (μ−LSL)/3σ]. 공정이 규격 한계 안에서 얼마나 안정적인지 보는 제조 표준 지표. 산업 표준은 Cpk ≥ 1.33(4σ 수준), 1.67은 5σ 수준의 우수 공정.

### 3-2. 구현해야 할 것 (현재 가장 근거 빈약 — "달성"으로 적혀 있으나 측정 0)
1. **"막힘" 조작적 정의를 규격으로 환산**: 현재 막힘 정의 = 4센서(토출압력·유량·모터전류·베어링진동) composite z-score ≥ 2.0 (`data_gen_test.py:42-48`). 이걸 측정 가능한 품질특성(CTQ)으로 전환하고 **LSL/USL을 명시**해야 Cpk 계산 가능.
2. **Cpk 계산 코드 추가**: `evaluate_test_metrics.py`에 USL·LSL·μ·σ 입력 → Cpk 산출 함수. 샘플 크기 명시.
3. **1.67의 근거**: 왜 1.67 목표인지(5σ 수준 정당화) + 실제 산출값 기록.

### 3-3. 주의
F1 0.95 ↔ Cpk 1.67은 **수학적으로 연결되지 않는 별개 지표**다. F1은 이상탐지 분류 성능, Cpk는 공정 산포 지표. 둘을 한 결과로 묶어 적으면 면접에서 "Cpk 어떻게 측정?" 질문에 막힌다. Cpk를 살리려면 **막힘률 % 측정과 한 묶음으로** 설계할 것 (§4 연계).

## 4. OEE 78%→85% / 막힘률 10%→2% (운영 성과 지표)

### 4-1. 무엇인가
- **OEE** = 가용성 × 성능 × 품질 (설비종합효율). 예지보전이 작동하면 계획 외 다운타임↓ → 가용성↑, 막힘 사전 감지 → 품질↑.
- **막힘률** = 전체 운영 시간(또는 사이클) 중 막힘 발생 비율(%).

### 4-2. 구현해야 할 것
1. **막힘률 측정 로직**: 현재 `evaluate_test_metrics.py`는 `anomaly_label`(0/1)만 측정. "막힘 사건 수 / 전체 구간"을 %로 환산하는 로직이 필요. 개입 전(baseline, 단일 센서 임계값) vs 개입 후(AE 시스템) 막힘률 비교 시나리오 설계.
2. **OEE 계산 파이프라인**: 가용성·성능·품질 각 구성요소를 합성 시뮬레이션에서 정의 → OEE 산출. 78%·85%의 출처 명시 (산업 평균? 시나리오 가정? — 현재 출처 표기 0).
3. **baseline 비교가 핵심**: "단일 센서 임계값 방식이면 막힘률 10%, AE 시스템이면 2%"를 **시뮬레이션에서 실제로 돌려** 수치를 산출해야 "10%→2%"가 목표가 아닌 검증값이 된다.

### 4-3. 완료 시 포트폴리오 격상 (가장 임팩트 큼)
- 발화: "단일 임계값 baseline 대비 막힘률을 10%에서 2%로 낮췄습니다" (검증 후) — 현재 P-002로 **본문 금지** 상태에서 해제 가능
- CEDR P-002 supersede 행 추가 (append-only 원칙: 기존 금지 행 보존 + 새 행에 측정 로직 명시)
