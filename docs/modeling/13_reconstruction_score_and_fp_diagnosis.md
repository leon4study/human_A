# 13. 복원오차 점수와 헛알람(FP) 진단

> 오토인코더(AE)가 "이상 점수"를 어떻게 만드는지, 그리고 그 점수를 피처별로 쪼개 "정상인데 왜
> 알람이 떴나(헛알람)"의 범인 피처를 찾는 법을 처음부터 쉽게 정리한다. 진단 코드는
> [fault_injection/nutrient_fp_diagnosis.py](../../fault_injection/nutrient_fp_diagnosis.py).

---

## 1. AE는 "복원을 못 한 정도"로 이상을 잰다

### 1-1. 복원이란

AutoEncoder는 입력을 좁은 통로로 **압축했다가 다시 펼쳐 원래대로 만드는** 모델이다.

```
입력(input) → [압축] → [복원] → 복원값(input')
```

정상 패턴만 학습했으므로, **정상 입력은 잘 복원**되고(input ≈ input'), **처음 보는 이상은 잘 복원하지 못한다**(input ≠ input').

> 비유: 늘 듣던 노래는 흥얼거려 재현할 수 있지만(정상), 처음 듣는 노래는 못 따라 부른다(이상).
> 못 따라 부른 정도가 곧 "이상 점수"다.

### 1-2. "못 맞춘 정도" = 복원오차 = (input − input')²

입력과 복원값의 차이가 곧 못 맞춘 정도다. **왜 제곱(²)을 하나:**

- 차이(input − input')는 +/− 부호가 있어 그냥 더하면 서로 **상쇄**된다.
- 제곱하면 (a) 부호를 없애 항상 양수가 되고, (b) **큰 차이를 더 강조**한다(차이 2배 → 기여 4배).
- 그래서 "얼마나 틀렸나"를 누적하기에 적합하다.

### 1-3. 윈도우 점수(MSE) = 피처별 제곱오차의 평균

한 윈도우(10분)에는 피처가 여러 개(F개) 있고, 피처마다 (input − input')²가 하나씩 나온다.
이를 **평균낸 값**이 그 윈도우의 점수다.

```
MSE(윈도우) = 평균_피처[ (input − input')² ]      # Mean Squared Error
```

MSE가 클수록 그 윈도우가 정상에서 벗어난 것. 이 MSE를 임계값과 비교해 알람을 띄운다(문서 03).

### 1-4. 왜 "scoring 피처"만 평균내나

AE는 **모든 피처를 복원**하지만, 점수에는 그 도메인이 **책임지는 피처(scoring features)만** 평균낸다.
시간·상태 컨텍스트(time_sin·pump_on 등)나 다른 도메인 소유의 외래 피처는 점수에서 **제외**한다.

- 이유: 그것들은 "정상을 설명하는 조건"이지 "이상 신호"가 아니다. 점수에 넣으면 헛알람·오귀인이 난다.
- 상세: [MODELING.md §5-2-1](../MODELING.md) 조건부/마스크 재구성 AE.

## 2. per-feature 제곱오차 "행렬"

점수(MSE)는 피처들을 평균내 **숫자 하나로 압축**한 것이다. 평균내기 **직전 단계**는 (윈도우 × 피처) 격자다.

|        | 피처1 | 피처2 | … | 피처F |
|--------|------|------|---|------|
| 윈도우1 | (입−복)² | (입−복)² | … | (입−복)² |
| 윈도우2 | … | … | … | … |
| …      |    |    |   |    |
| 윈도우N | … | … | … | … |

이것이 **N×F 제곱오차 행렬**이다. 코드에서는 `sq = (Xs - pred) ** 2` 한 줄이 이 행렬을 만든다.
두 방향으로 읽는다:

- **가로(피처 방향) 평균** → 윈도우별 점수(MSE). "이 10분이 이상한가?"
- **세로(윈도우 방향)** → 특정 피처가 어느 윈도우에서 많이 틀렸나. "이 센서가 언제 안 맞나?"

> 즉 점수가 "이 윈도우가 이상하다"까지만 말한다면, 행렬의 세로 방향은 "**어느 피처 때문에** 이상하다"까지 알려준다. 헛알람 진단(아래)은 바로 이 세로 방향을 본다.

---

## 3. 헛알람(FP) 진단법 — "어느 피처가 범인인가"

### 3-1. 헛알람이란

**정상(고장 없는)** 데이터인데 점수 ≥ 임계 → 알람이 뜬 것 = 거짓 양성(False Positive, FP).
어떤 도메인이 FP가 잦다면, **정상인데도 AE가 잘 복원하지 못하는 피처**가 있다는 뜻이다.

### 3-2. 범인 피처 찾기

FP 윈도우의 피처별 제곱오차를, **정상-비알람** 윈도우와 비교한다.

- `e_fp`  = FP 윈도우들에서 그 피처의 평균 오차.
- `e_clean` = 정상-비알람 윈도우들에서 그 피처의 평균 오차.
- **배수 = e_fp / e_clean** — 크면 그 피처가 헛알람 때만 유독 크게 틀린다는 뜻.
- **FP비중 = (그 피처 오차) / (FP 윈도우 MSE 합)** — 한 피처가 99%면 그 하나가 거의 모든 헛알람의 원인.

### 3-3. 판정과 처방

- **한두 피처에 쏠림** → 그 피처를 **채점에서 제외**하거나 **robust화(평활)** 하거나 **파생변수로 대체** → 가벼운 근본수정.
- **여러 피처에 고르게 분산** → 모델 용량·학습 부족이 원인(무거움). 이 경우 임시로 도메인 분리(voting 제외) 운영이 현실적.

## 4. nutrient 사례 (2026-06-12)

nutrient는 FP 폭주(과거 EVAL FP의 94%)로 overall voting에서 제외돼 있었다. 위 진단을 돌린 결과:

| 피처 | FP 오차 | 정상 오차 | 배수 | FP비중 |
|---|---|---|---|---|
| **ph_trend_30** | 4.924 | 0.0017 | **2933배** | **99%** |
| 나머지(salt_accumulation_delta·drain_ec 등) | ≤ 0.006 | … | 2~9배 | ~0% |

→ **단일 피처 `ph_trend_30` 하나가 nutrient 헛알람의 99%를 일으킨다**(정상인데 복원오차가 평소의 2933배). Phase B의 time_cos 사태(단일 피처 거대오차 → 헛알람)와 같은 패턴.

**처방(가벼움)**: `ph_trend_30`를 nutrient **채점에서 제외**하거나 **robust화**(rpm_slope·temp_slope처럼 rolling 평균 후 추세) → FAR 1.2%→~0% 예상 → nutrient를 알람·RCA 어디든 깨끗이 포함 가능. 단, 그 피처가 실제 고장 검출에 기여하는지 확인 후 결정한다(빼도 mix_ph·mix_ec·pid_error가 검출을 carry할 것으로 본다).

## 6. 근본 원인과 처방 (2026-06-12 스케일 진단)

ph_trend_30 폭발의 진짜 원인은 **스케일러 종류가 아니라 피처의 무거운 꼬리**였다(`ph_trend_scale_diagnosis.py`):

- MinMax 학습 범위 [−0.0023, 0.0024]인데, held-out 정상값의 0.9%가 그 범위를 벗어남(P99.9=0.015 = max의 6배).
- 그 꼬리값이 MinMax로 외삽돼 스케일값 2.5~3.9(>[0,1]) → AE가 정상 클러스터(0.5)만 배워 복원 0.5 고정 → 오차 폭발.

**방법별 판정:**

| 방법 | 판정 | 이유 |
|---|---|---|
| RobustScaler(A3) | ✗ 기각 | 스케일러 종류 문제 아님. IQR이 작아 꼬리를 더 크게 외삽(악화) |
| 클리핑(A2) | △ 부적합 | 정상 꼬리(FP)와 고장 신호 둘 다 큰 ph_trend라 크기로 못 가름 → 신호도 잘림 |
| **평활/robust(A1)** | ✅ 채택 | FP는 순간 스파이크·고장은 지속 추세 → diff 전 평활로 *시간 구조*로 분리 |

**미래 방향 (지표 재설계)**: 꼬리가 두꺼운 파생변수에는 **log / signed-log(`sign(x)·log1p(|x|)`)** 변환이 더 근본적이다 — 큰 값을 압축해 외삽을 원천 차단하면서 신호의 크기 정보를 (압축된 형태로) 보존한다(clip이 신호를 자르는 것과 대비). ph_trend_30뿐 아니라 다른 추세·차분 파생변수도 분포 꼬리를 점검해 일괄 재설계할 것. (현재는 A1 robust로 우선 처리, 재설계는 별도 패스.)
