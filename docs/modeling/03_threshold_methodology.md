# 03 — Dynamic Threshold 산정 방법론

"dynamic threshold가 안정적으로 산정되지 않는다"는 문제에 대한 정공법입니다. 핵심 전환은 **직관적 σ 조정에서, 운영 제약을 만족하는 지점을 데이터로 선택**하는 방식으로 옮기는 것입니다.

---

## 1. 문제 정의 — 현재 무엇이 안 되는가

포트폴리오에서 언급하는 "dynamic threshold"의 실체는 AE 복원오차(MSE) 분포의 σ 컷으로 만든 3단계 알람입니다 ([../portfolio_interview_facts.md](../portfolio_interview_facts.md)).

| 단계 | 현재 기준 |
|---|---|
| 주의(Caution) | μ + 2σ |
| 경고(Warning) | μ + 3σ |
| 심각(Critical) | μ + 6σ |

관측된 한계 (MODEL_CHANGELOG 정량평가)
- NUTRIENT: 임계치가 학습 분포 대비 과도하게 낮게 산정돼 FP의 94%가 집중됐습니다(precision 0.15).
- cutoff를 2, 3으로 올리면 recall이 0.20에서 0.02로 급락합니다. 한 단계만 올려도 거의 검출하지 못합니다.
- 도메인마다 분포가 달라 동일한 σ 정책이 맞지 않습니다.

---

## 2. 근본 원인 — σ 고정의 가정 위반

`μ + kσ`는 복원오차가 정규분포라는 가정을 전제합니다. 그러나
- AE 복원오차는 일반적으로 한쪽으로 긴 꼬리(right-skewed) 분포이며 정규분포가 아닙니다.
- 도메인마다 꼬리 두께가 다른데 동일한 `k(2/3/6)`를 적용하면, 어떤 도메인은 과민(NUTRIENT), 어떤 도메인은 과둔(HYDRAULIC recall 5%)해집니다.
- 따라서 분포 가정을 두지 않는 방식으로 전환해야 합니다.

---

## 3. 방법론 — 라벨 유무로 구분

### 3-A. 검증셋에 라벨이 일부라도 있으면: PR curve로 선택

임계치를 운영 제약을 만족하는 지점으로 데이터에서 선택합니다.

```
1. validation 구간에서 임계치를 스윕(sweep)
2. 각 임계치의 (Precision, Recall, FAR)를 계산해 PR curve / FAR curve 작성
3. 운영 제약(예: FAR ≤ 5%)을 만족하는 구간에서 recall이 최대인 지점 선택
4. 그 임계치를 test 구간에서 최종 평가 (validation ≠ test, 누수 방지)
```

이 방식이면 "NUTRIENT 임계치가 너무 낮다"가 직관이 아니라 "FAR ≤ 5% 제약을 만족하는 지점을 선택한 결과"로 정량화됩니다. 도메인별로 독립 선택하므로 동일 정책 강제 문제도 해소됩니다.

### 3-B. 라벨이 전혀 없으면: percentile 기반

정상 데이터 복원오차의 분위수(percentile)를 임계치로 사용합니다. σ보다 꼬리에 강건합니다.

| 단계 | percentile 기반 (제안) |
|---|---|
| 주의 | 정상 오차의 P95 |
| 경고 | P99 |
| 심각 | P99.9 |

- 정규분포 가정 없이 "정상의 상위 X%를 벗어나면 이상"으로 직접 정의합니다.
- 도메인마다 분포가 달라도 각자의 percentile이므로 자동 보정됩니다.
- 단점: 정상 데이터 순도에 민감합니다 ([02 §2](02_evaluation_design.md)). 정상에 이상이 섞이면 percentile이 오염됩니다.

## 4. 도메인별 보정 — 동일 정책 강제를 버린다

현재 `EXCLUDE_FROM_OVERALL = {"nutrient"}`는 증상 차단(voting에서 제외)이며 근본 수정이 아닙니다.

근본 방향 두 갈래
1. 임계치를 도메인별로 데이터에서 선택(3절)하여, NUTRIENT도 자기 분포에 맞는 임계치를 갖게 합니다.
2. NUTRIENT 피처 자체를 수정합니다. A-3에서 raw 센서 target 재편을 시도했으나 전 도메인이 악화돼 롤백했습니다. 재시도 시 [01 재현성](01_experiment_protocol.md)을 확보한 뒤, 한 도메인만 변경하고 다른 도메인이 불변임을 검증해야 합니다.

A-3 교훈: NUTRIENT 하나를 수정하려다 변경하지 않은 motor 성능이 크게 저하됐습니다(F1 0.527→0.106). 임계치 방법론(3절)이 피처 수정(A-3)보다 부작용이 작으므로 임계치 조정부터 시도하길 권장합니다.

## 4-2. 레짐 인지 임계값 — 기동(startup) 전용 band (실험 완료 2026-06-04)

기동 직후는 정상 과도 응답이라 재구성 오차가 크다. 현재는 기동 윈도우를 통째로 Normal로 억제하는데
(`is_startup_phase` 게이트), 이러면 **비정상 기동**(평소 압력이 90까지 튀다가 그날 130으로 튀는 경우)도
함께 무시된다. 정상 행동이 운전 상태에 따라 다르므로, 이상도 그 상태 기준으로 정의하는 것이 정석이다
(산업 예지보전의 regime-based normalization). 임계값을 상태별로 따로 두는 것 — 즉 임계선이 "울퉁불퉁"해진다.

전략을 데이터로 비교했다([fault_injection/startup_strategy_eval.py](../../fault_injection/startup_strategy_eval.py)).
점수는 현재 모델로 한 번 뽑고 결정 전략만 오프라인으로 갈아끼워 공정 비교(비정상 기동은 기동 윈도우의
압력·모터전력을 배수로 상승시켜 생성).

| 전략 | 정상기동 FAR | 비정상기동 recall(1.1×~1.5×) |
|---|---|---|
| A 통째게이트(현재) | 0.000 | 0.000 — 전부 놓침 |
| B regime band(정상기동 p99) | 0.033 | 1.000 |
| C 처리없음(정상상태 임계 적용) | 1.000 | 1.000 |

결론: **B(레짐 인지 band)** 채택. A는 비정상 기동을 100% 놓치고(사각지대), B는 정상기동 오탐 3.3%만으로
비정상 기동을 살짝(1.1×)부터 전부 잡는다. 정상 기동 점수가 촘촘히 뭉쳐(median 0.00088, max 0.00091)
band가 칼같이 잡히기 때문. C는 통째게이트가 왜 도입됐는지 보여주는 대조군(FAR 100%).

구현(완료, 2026-06-04): 학습 시 정상상태 band와 함께 **기동용 band**(정상 기동 점수의 백분위
p99/p99.5/p99.9)를 산출해 config의 `threshold_startup`에 저장([train.py](../../src/train.py)).
추론([inference_api.py](../../src/inference_api.py))·평가([evaluate_test_metrics.py](../../src/evaluate_test_metrics.py))는
환경변수 `STARTUP_MODE`(`gate` | `regime`, 기본 `regime`)로 분기한다. regime이면 기동 윈도우를
기동용 band로 재판정하고, band가 없는 구버전 config는 자동으로 gate(통째 억제)로 폴백한다.
실제 regime 동작은 **재학습으로 `threshold_startup`이 생성된 뒤** 활성화된다.

단서: ① 월1 기동 표본이 30개로 적어 band 추정이 거칠다(재학습 시 더 많은 기동 표본으로 안정화).
표본 <20이면 train.py가 band 산출을 생략한다. ② 10분 집계가 mean이면 짧은 피크가 희석될 수 있어,
기동 윈도우에 max/p95 피처 보강을 검토한다. ③ 위 비교 수치는 구버전 서빙 모델 기준이며 재학습 후
갱신되나, "regime band ≫ 통째게이트" 결론은 구조적이다.

## 5. 검증 — 임계치를 바꾸면 무엇을 보는가

임계치 변경 실험의 표준 측정

```
변경 전후로 experiments.csv에 두 줄 기록 (01 §3):
  - 도메인별 P / R / F1 / FAR
  - overall(no_nutrient) P / R / F1 / FAR
점검:
  - 목표 제약(FAR ≤ 5%)을 만족했는가
  - recall이 유지 또는 향상됐는가 (임계치를 올려 FAR만 낮추고 recall을 희생하면 무의미)
  - 다른 도메인이 영향받지 않았는가 (임계치는 도메인 독립이어야 정상)
```

## 6. 알람 사양 변경 예정 (강사 피드백)

| 항목 | 현재 | 목표 |
|---|---|---|
| σ 레벨 | (2σ, 3σ, 6σ) | (1σ, 2σ, 3σ) |
| 디바운싱 | "N분 연속" 단순 룰 | 도메인별 연속 N회 (주의 3 / 경고 5 / 심각 7 초안) |

- σ 레벨을 낮추면 민감도(recall)가 오르지만 FP도 증가하므로, 디바운싱(연속 N회)으로 스파이크 노이즈를 상쇄하는 것이 핵심 설계입니다.
- 이 변경도 3절 방법론과 충돌하지 않습니다. σ 레벨을 낮추든 percentile을 쓰든, 최종 판단은 "운영 제약(FAR)을 만족하는가"라는 단일 기준으로 합니다.
- 디바운싱 도입 시 평가 단위가 샘플에서 연속 구간으로 바뀌므로 [02 평가 설계](02_evaluation_design.md)의 메트릭 정의도 함께 갱신합니다.

## 7. 권장 진행 순서

```

2. EVAL을 validation/test로 분리 (02 §1)
3. 3-A(라벨 있음) PR curve 스윕으로 도메인별 임계치 선택
   라벨 신뢰가 낮으면 3-B percentile 병행 실험
4. experiments.csv로 변경 전후 비교 (01 §3)
5. NUTRIENT가 제약을 만족하면 EXCLUDE_FROM_OVERALL 해제 검토
```
