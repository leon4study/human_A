# 03 — Dynamic Threshold 산정 방법론

"dynamic threshold(상황에 따라 자동으로 정해지는 정상/이상 경계값)가 안정적으로 정해지지 않는다"는 문제를 정면으로 다룹니다. 핵심은 접근 방식을 바꾸는 것입니다. 지금까지의 "감으로 σ(표준편차 — 값들이 평균에서 얼마나 흩어져 있는지를 나타내는 값)를 조정"하던 방식에서, **운영상 지켜야 할 조건(예: 오탐을 일정 수준 이하로 유지)을 만족하는 지점을 데이터로 직접 골라내는** 방식으로 옮깁니다.

---

## 1. 문제 정의 — 현재 무엇이 안 되는가

포트폴리오에서 말하는 "dynamic threshold"는 사실, AE 복원오차(MSE — 모델이 정상이라고 본 모습과 실제 입력이 얼마나 어긋났는지를 하나의 점수로 만든 값) 분포를 σ(표준편차) 기준으로 잘라 만든 3단계 알람입니다 ([../portfolio_interview_facts.md](../portfolio_interview_facts.md)).

| 단계 | 현재 기준 |
|---|---|
| 주의(Caution) | μ + 2σ |
| 경고(Warning) | μ + 3σ |
| 심각(Critical) | μ + 6σ |

관측된 한계 (MODEL_CHANGELOG 정량평가)
- NUTRIENT: 경계값이 학습 데이터 분포에 비해 너무 낮게 잡혀서, 전체 오탐(FP — 정상을 이상이라고 잘못 띄운 것)의 94%가 이 도메인 한 곳에 몰렸습니다(precision 0.15).
- 경계 단계(cutoff)를 2, 3으로 올리면 recall(실제 이상 중 잡아낸 비율)이 0.20에서 0.02로 뚝 떨어집니다. 한 단계만 올려도 거의 잡지 못합니다.
- 도메인마다 분포가 달라, 똑같은 σ 정책을 모두에 적용하면 맞지 않습니다.

---

## 2. 근본 원인 — σ 고정의 가정 위반

`μ + kσ`(평균 + k×표준편차)라는 공식은 복원오차가 정규분포(좌우 대칭의 종 모양)를 따른다고 가정합니다. 그러나
- AE 복원오차는 보통 오른쪽으로 긴 꼬리를 가진(right-skewed) 분포여서, 정규분포가 아닙니다.
- 도메인마다 꼬리의 두께가 다른데도 똑같은 `k(2/3/6)`를 적용하면, 어떤 도메인은 너무 예민하게(NUTRIENT), 어떤 도메인은 너무 둔하게(HYDRAULIC recall 5%) 반응합니다.
- 따라서 분포 모양을 가정하지 않는 방식으로 바꿔야 합니다.

---

## 3. 방법론 — 라벨 유무로 구분

### 3-A. 검증셋에 라벨이 일부라도 있으면: PR curve로 선택

임계치를 운영 제약을 만족하는 지점으로 데이터에서 선택합니다.

```
1. validation 구간에서 임계치를 스윕(sweep)
2. 각 임계치의 (Precision, Recall, FAR)를 계산해 PR curve / FAR curve 작성
3. 운영 제약(예: FAR ≤ 5%)을 만족하는 구간에서 recall이 최대인 지점 선택
4. 그 임계치를 test 구간에서 최종 평가 (validation ≠ test, 누수 방지)
```

이렇게 하면 "NUTRIENT 임계치가 너무 낮다"는 말이 감이 아니라, "FAR(오탐률 — 정상을 이상이라고 잘못 띄운 비율)을 5% 이하로 지킨다는 조건을 만족하는 지점을 고른 결과"라는 수치로 설명됩니다. 도메인마다 따로 고르므로, 모두에 같은 정책을 강요하던 문제도 사라집니다.

### 3-B. 라벨이 전혀 없으면: percentile 기반

정상 데이터에서 나온 복원오차의 분위수(percentile — 값을 작은 순서로 줄 세웠을 때 몇 % 지점에 있는지)를 경계값으로 씁니다. σ 방식보다, 꼬리가 긴 분포에서 덜 흔들립니다(강건합니다).

| 단계 | percentile 기반 (제안) |
|---|---|
| 주의 | 정상 오차의 P95 |
| 경고 | P99 |
| 심각 | P99.9 |

- 정규분포 가정 없이 "정상의 상위 X%를 벗어나면 이상"으로 직접 정의합니다.
- 도메인마다 분포가 달라도 각자의 percentile이므로 자동 보정됩니다.
- 단점: 정상 데이터 순도에 민감합니다 ([02 §2](02_evaluation_design.md)). 정상에 이상이 섞이면 percentile이 오염됩니다.

## 4. 도메인별 보정 — 동일 정책 강제를 버린다

현재 `EXCLUDE_FROM_OVERALL = {"nutrient"}` 설정은 증상만 막는 임시 조치입니다(전체 알람을 모으는 투표에서 nutrient 도메인을 빼는 것). 근본 수정이 아닙니다.

근본 방향 두 갈래
1. 임계치를 도메인별로 데이터에서 선택(3절)하여, NUTRIENT도 자기 분포에 맞는 임계치를 갖게 합니다.
2. NUTRIENT 피처 자체를 수정합니다. A-3에서 raw 센서 target 재편을 시도했으나 전 도메인이 악화돼 롤백했습니다. 재시도 시 [01 재현성](01_experiment_protocol.md)을 확보한 뒤, 한 도메인만 변경하고 다른 도메인이 불변임을 검증해야 합니다.

A-3 교훈: NUTRIENT 하나를 수정하려다 변경하지 않은 motor 성능이 크게 저하됐습니다(F1 0.527→0.106). 임계치 방법론(3절)이 피처 수정(A-3)보다 부작용이 작으므로 임계치 조정부터 시도하길 권장합니다.

## 4-2. 레짐 인지 임계값 — 기동(startup) 전용 band (실험 완료 2026-06-04)

펌프가 막 켜진 직후(기동 직후)는 정상적인 과도 응답이라 복원오차가 원래 큽니다. 현재는 기동 구간(윈도우)을
통째로 Normal로 눌러 버립니다(`is_startup_phase` 게이트). 그런데 이러면 **비정상 기동**(평소엔 압력이 90까지만
튀다가 그날 130으로 튀는 경우)까지 함께 무시됩니다. 정상적인 동작이 운전 상태에 따라 달라지므로, 이상도 그
상태를 기준으로 정의하는 것이 정석입니다(산업 예지보전에서 말하는 regime-based normalization — 운전 상태별로
정상 기준을 따로 두는 것). 즉 경계선이 상태마다 달라져 "울퉁불퉁"해집니다.

이 전략들을 데이터로 비교했습니다([fault_injection/startup_strategy_eval.py](../../fault_injection/startup_strategy_eval.py)).
점수는 현재 모델로 한 번만 계산하고, 판정 전략만 따로 바꿔 끼워 공정하게 비교했습니다(비정상 기동은 기동
윈도우의 압력·모터전력을 배수로 끌어올려 만들었습니다).

| 전략 | 정상기동 FAR | 비정상기동 recall(1.1×~1.5×) |
|---|---|---|
| A 통째게이트(현재) | 0.000 | 0.000 — 전부 놓침 |
| B regime band(정상기동 p99) | 0.033 | 1.000 |
| C 처리없음(정상상태 임계 적용) | 1.000 | 1.000 |

결론: **B(레짐 인지 band)** 채택. A는 비정상 기동을 100% 놓치고(사각지대), B는 정상기동 오탐 3.3%만으로
비정상 기동을 살짝(1.1×)부터 전부 잡는다. 정상 기동 점수가 촘촘히 뭉쳐(median 0.00088, max 0.00091)
band가 칼같이 잡히기 때문. C는 통째게이트가 왜 도입됐는지 보여주는 대조군(FAR 100%).

구현(완료, 2026-06-04): 학습 시 정상상태 band와 함께 **기동용 band**(정상 기동 점수의 백분위
p99/p99.5/p99.9)를 산출해 config의 `threshold_startup`에 저장([train.py](../../src/train.py)).
추론([inference_api.py](../../src/inference_api.py))·평가([evaluate_test_metrics.py](../../src/evaluate_test_metrics.py))는
환경변수 `STARTUP_MODE`(`gate` | `regime`, 기본 `regime`)로 분기한다. regime이면 기동 윈도우를
기동용 band로 재판정하고, band가 없는 구버전 config는 자동으로 gate(통째 억제)로 폴백한다.
실제 regime 동작은 **재학습으로 `threshold_startup`이 생성된 뒤** 활성화된다.

단서: ① 월1 기동 표본이 30개로 적어 band 추정이 거칠다(재학습 시 더 많은 기동 표본으로 안정화).
표본 <20이면 train.py가 band 산출을 생략한다. ② 10분 집계가 mean이면 짧은 피크가 희석될 수 있어,
기동 윈도우에 max/p95 피처 보강을 검토한다. ③ 위 비교 수치는 구버전 서빙 모델 기준이며 재학습 후
갱신되나, "regime band ≫ 통째게이트" 결론은 구조적이다.

## 4-3. 임계값 일반화 — 학습이 아니라 held-out에서 보정한다 (방법론, 2026-06-08)

§4-2 단서 ①(기동 표본이 적어 band 추정이 거칠다)을 held-out 평가셋으로 정량 확인하면서 얻은
일반 교훈이다. 핵심은 특정 수치가 아니라 "이렇게 검증한다"는 절차다.

실험 패턴:
1. FAR을 운전 레짐으로 분해한다 — 정상상태 vs 기동(startup)을 나눠 각각의 헛알람률을 본다.
   전체 FAR이 낮아도 특정 레짐(예: 기동), 특정 도메인(예: motor)에 몰려 있을 수 있다.
2. 처리 전략을 같은 점수에 갈아끼워 before/after를 만든다 — 처리없음 / 통째게이트 / regime band.
   같은 데이터에서 regime band가 기동 헛알람을 얼마나 줄이는지(사용자 작업의 효과)를 본다.
3. 그 band를 "학습에 안 쓴 held-out 기동"에 적용해 본다.

관측된 패턴(값이 아니라 현상): 학습 기동의 분위(p99)로 그은 band가 held-out 기동에서는 nominal
목표(1%)보다 훨씬 자주 넘긴다. 원인이 둘 겹친다 — (a) AE가 학습 기동의 특정 노이즈를 외워 처음 보는
기동을 더 크게 본다(일반화 갭), (b) 유한 표본의 경험적 분위가 진짜 분위를 과소추정한다(추정 오차).
둘 다 "band가 실제보다 좁다"로 귀결된다.

원칙(실무 표준): 임계값은 "학습 데이터"가 아니라 "학습에 안 쓴 검증/held-out 데이터"에서 목표 FAR로
보정한다. 경험적 분위를 그대로 쓰지 말고 안전 마진(더 보수적 분위·배수)을 둔다. 가장 원리적으로는
conformal prediction처럼 held-out으로 오탐률 상한을 유한표본 보장하는 보정을 쓴다. 즉 §3-B의
percentile도 "어느 데이터에서 분위를 재느냐"가 핵심 — 학습이 아니라 held-out이어야 한다.

도구: held-out 평가셋은 [build_faulty_testset.py](../../fault_injection/build_faulty_testset.py)가
"학습과 다른 seed"로 만든 독립 정상 base 위에 4종 고장을 주입해 생성한다(정상 노이즈가 학습과 겹치지
않아 FAR이 정직하고, 임계값을 여기서 보정하면 일반화 갭이 반영된다).

## 5. 검증 — 임계치를 바꾸면 무엇을 보는가

임계치 변경 실험의 표준 측정

```
변경 전후로 experiments.csv에 두 줄 기록 (01 §3):
  - 도메인별 P / R / F1 / FAR
  - overall(no_nutrient) P / R / F1 / FAR
점검:
  - 목표 제약(FAR ≤ 5%)을 만족했는가
  - recall이 유지 또는 향상됐는가 (임계치를 올려 FAR만 낮추고 recall을 희생하면 무의미)
  - 다른 도메인이 영향받지 않았는가 (임계치는 도메인 독립이어야 정상)
```

## 6. 알람 사양 변경 예정 (강사 피드백)

| 항목 | 현재 | 목표 |
|---|---|---|
| σ 레벨 | (2σ, 3σ, 6σ) | (1σ, 2σ, 3σ) |
| 디바운싱 | "N분 연속" 단순 룰 | 도메인별 연속 N회 (주의 3 / 경고 5 / 심각 7 초안) |

- σ 레벨을 낮추면 민감도(recall)가 오르지만 FP도 증가하므로, 디바운싱(연속 N회)으로 스파이크 노이즈를 상쇄하는 것이 핵심 설계입니다.
- 이 변경도 3절 방법론과 충돌하지 않습니다. σ 레벨을 낮추든 percentile을 쓰든, 최종 판단은 "운영 제약(FAR)을 만족하는가"라는 단일 기준으로 합니다.
- 디바운싱 도입 시 평가 단위가 샘플에서 연속 구간으로 바뀌므로 [02 평가 설계](02_evaluation_design.md)의 메트릭 정의도 함께 갱신합니다.

```

2. EVAL을 validation/test로 분리 (02 §1)
3. 3-A(라벨 있음) PR curve 스윕으로 도메인별 임계치 선택
   라벨 신뢰가 낮으면 3-B percentile 병행 실험
4. experiments.csv로 변경 전후 비교 (01 §3)
5. NUTRIENT가 제약을 만족하면 EXCLUDE_FROM_OVERALL 해제 검토
```
