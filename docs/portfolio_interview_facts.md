### 0-1. 추정치의 두 층 구조 (면접 방어의 핵심)

모든 비즈니스 KPI는 두 층으로 되어 있고, **경계를 스스로 라벨링**하는 게 정직성+방어력이다:

```
[측정 근거]  ──연결──▶  [정당성 / 다운타임 서사]  ──산출──▶  [KPI 추정치]
 데이터·모델에서 잰 것      운영 가정으로 잇는 인과 논리        OEE·막힘률·돈
```

- **측정 근거**: 막힘 에피소드 검출 12/12(100%, 16건·4유형 주입), 평균 lead-time ~28h, 원인 도메인 정확 귀인(RCA), AE FAR 1.8% < baseline 3.1%, 유량 Cpk 측정. → 코드/모델 산출(가정 아님). ※ 검출·lead-time은 단일센서 baseline과 동등하고, AE의 측정된 우위는 **FAR ~1.7배↓ + 도메인 RCA**다(운영점 P99.5·tumbling 정합 후). 4유형 모두 원인 도메인을 정확히 짚는다(nutrient 포함, Phase P에서 trimmed-mean으로 해소).
- **정당성(다운타임 서사)**: 관수설비는 "멈추면 작물이 비가역적으로 죽는다" → 다운타임 비용이 비선형. AE가 (a) 원인 도메인 즉시 귀인 → 진단시간↓, (b) ~28h 전 감지 → 돌발정지를 계획정비로 전환 → 다운타임 회피. ← 측정 능력을 KPI로 잇는 다리.
- **KPI 추정**: 그 다리 위에서 가용성↑ → OEE·막힘률·손실예방 추정.

### 0-3. 다운타임 정당성 — 수치 가정 (확인 요망)

다운타임 서사를 정량화하는 운영 가정. **n(다운타임 1건 길이)은 현업 감각으로 확정 필요 — 아래는 잠정 예시이며 임의 산정 금지**:

- **다운타임 1건 길이 n** ≈ `8h` *(← 운영 가정, 확인 요망)*. 막힘이 완전 정지로 진행 시 발견+진단+정비/교체 소요.
- **AE 효과**: ~28h 전 감지 + 원인 도메인 즉시 귀인 → 돌발정지(n시간 비계획)를 계획정비로 전환 → 작물 사멸 임계 도달 전 대응 → 다운타임 상당분 회피.
- **가용성 기여**: 비계획 다운타임 회피분이 그대로 Availability↑ → OEE 가용성 축 개선 근거.

> **왜 이 도메인에서 정당성이 강한가**: 공장 라인은 멈추면 생산량만 잃지만, 관수설비는 멈추면 **살아있는 작물을 비가역적으로 잃는다**. 그래서 다운타임 비용이 비선형(임계 초과 시 급증)이고, 예지보전(=다운 회피)의 가치가 이 도메인에서 특히 크다 → OEE에서 가용성을 지배 축으로 두는 정당성.

> 두 번째는 1000평 딸기 스마트팜의 양액 펌프 막힘 예지보전이었습니다. 한 번 펌프가 막히면 4000만원 손실이 나는 구조라, 막힘을 사전에 탐지해 알림을 주는 시스템이 필요했습니다. 그런데 정상·고장 라벨이 거의 없었고 기온이나 작물 상태가 바뀌면 정상의 범위 자체가 함께 움직여서, 단일 기준으로는 안정적인 알람을 잡기 어려웠습니다. 그래서 모터·수력·양액·구역의 네 도메인으로 나누고, 각 도메인의 평상시 패턴을 학습해 동적으로 움직이는 임계치(다이나믹 쓰레시홀드)를 만든 뒤, 그 임계치를 벗어나는 정도로 이상을 잡는 모델을 올렸습니다. 네 모델 모두 정상·이상 구분에서 F1 0.95를 넘겼고, 1000평 농장 기준 연 4000만원 손실 예방 효과로 환산했습니다.

## 4. 향후 코드/문서 수정 시 점검 체크리스트

다음 항목이 코드 또는 docs에서 변경되면 위 발화(1분 자기소개 + 면접 답변)도 같이 갱신해야 함:

- [ ] **F1 0.95 수치 변동** — 4도메인 중 하나라도 F1이 떨어지면 "95% 정확도" 표현 점검. nutrient 도메인 오탐 문제(현재 voting 제외 운영 중) 근본 수정 시 발화 갱신 필요
- [ ] **4도메인 분리 구성 변경** — motor/hydraulic/nutrient/zone_drip 외 추가/통합 시 "모터·수력·양액·구역" 표현 갱신
- [ ] **AutoEncoder → 다른 모델 전환** — "평상시 패턴을 학습해 그 패턴에서 벗어나는 정도" 표현 검토
- [ ] **다이나믹 쓰레시홀드(6시그마 알람) 변경** — 현재 (2σ, 3σ, 6σ) 운영 중이지만 강사 피드백에 따라 (1σ, 2σ, 3σ) + 디바운싱 전환 예정. 변경 시 발화 표현은 그대로 유지 가능 (구체 수치 노출 안 함)
- [ ] **연 4000만원 환산 가정 변경** — 1000평 기준·작물 종류·고품질 비율 가정이 바뀌면 환산값 재계산 + 발화 수치 갱신
- [ ] **막힘률 % 표현 부활 금지** — "막힘률 10%→2%"는 측정 로직 없는 목표 수치. 코드에 실제 막힘률 측정 로직이 새로 들어오기 전까지는 발화에 다시 넣지 말 것
- [ ] **농장 실측 배포 시작** — 합성 데이터가 아니라 실제 농장 운영 결과 나오면 "1000평 딸기 스마트팜" 가정 표현 → 실측 기반으로 갱신, "환산" 단어 → "달성"으로 변경 가능

## 5. 후속 질문 대비 카드 (본문에 안 넣은 디테일)

면접관이 후속 질문하면 풀어 답할 수 있도록 본문에 안 넣고 보류한 사실들:

- **"막힘" 조작적 정의** = 4센서(토출압력·유량·모터전류·베어링진동) composite z-score ≥ 2.0 [`data_gen_test.py:42-48`]
- **데이터 규모** = 45개 변수 × 1분 단위 × 3개월 (약 130,000행) 가상 합성. 1개 양액펌프 + 3개 점적 구역 (zone1 활용)
- **SHAP 자동화** = 도메인별 타깃 변수에 LightGBM SHAP → 상위 25% 추출 → 2개 이상 타깃 공통 피처만 robust 채택 [`docs/MODELING.md:§3`]
- **VIP 피처 강제 주입** = time_sin/cos, pump_on 등 시간·상태 컨텍스트 피처는 SHAP 외 강제 주입 (정상 기동 overshoot 구분 위해)
- **6시그마 3단계 알람** = 정상 MSE 분포에서 μ+2σ(주의)/3σ(경고)/6σ(치명) 자동 산출. 기동 직후 5분은 `alarm_level=0` 강제
- **nutrient 도메인 예외** = EVAL 구간 FP 581건 중 547건(94%)이 nutrient → 현재 overall voting에서 제외 운영
- **본인 역할** = 5인 팀(분석 3 + 백엔드 1 + 프론트 1) 중 팀장. 가상 데이터 생성, 전처리 5단계 파이프라인, 4도메인 AE 학습, SHAP 자동화, 추론 API 직접 구현 [`docs/PROJECT_BRIEF.md:§1-1`]
- **기간** = 2026-04-07 ~ 04-23 (약 2.5주)
- **알려진 한계** = 재학습 비결정성(`random_state=42` 설정에도 다른 모델 산출, `n_jobs=-1` 의심), 알람 사양 최종화 미완료, nutrient 근본 수정 검토 중

## 7. 알려진 한계 (docs에만 — 헤드라인엔 안 넣음)

면접에서 깊이 물으면 정직하게 답할 한계들. 헤드라인은 강점 중심으로 두되, 여기 명시해 자기 인지를 보인다(2026-06-12 검증 기준).

- **(해소됨, Phase P) RCA 오귀인·nutrient voting 제외** — 옛 약점: nutrient 막힘을 motor로 오귀인 + nutrient가 FP로 voting 제외돼 검출 마진이 얇음. **2026-06-12 해결** — 원인은 ph_trend_30의 OOD 외삽이 평균 점수를 지배한 것이라, **trimmed-mean 로버스트 집계**(nutrient만 상위1 오차 제외; 문헌 Skewed-Data AE 2023·Unreliable-AE 2025)로 FP를 차단하고 nutrient를 voting+RCA에 포함. 검출 12/12·4유형 귀인 정확. (`inference_core.reconstruction_score`, docs/modeling/13 §6, MODEL_CHANGELOG Phase P)
- **윈도우 F1 0.63** — 윈도우 단위 F1=0.63(precision/recall ~0.63). 막힘 초반(전조 미미) 구간이 label=1이지만 안 울리는 게 정상이라 윈도우 FN이 구조적으로 쌓임. **에피소드 단위 검출은 12/12**라 발화는 에피소드 검출·FAR·RCA로 한다(윈도우 F1·"F1 0.95" 헤드라인 지양).
- **소표본** — held-out 막힘 에피소드 12건(소표본). 운영점·검출은 강한 고장(severity 0.8~1.0) 기준이라, 더 미세한 전조까지의 일반화는 미검증.
- **임계 윈도잉 영구화 미완** — 현재 운영점 정합은 config 핸드에딧(tumbling P99.5). train.py가 임계를 sliding으로 계산하므로, 재학습 시 다시 어긋난다 → train.py 수정으로 영구화 필요(`models/_threshold_backup_pre_P995`에 원본 보존).
- **재학습 비결정성** — `random_state=42`에도 산출 모델이 다름(`n_jobs=-1` 의심). 알람 사양 최종화 미완.
